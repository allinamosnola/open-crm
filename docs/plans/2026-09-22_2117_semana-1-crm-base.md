# MVP CRM dental + bot WhatsApp — Plan Semana 1 (CRM base)

## Contexto
Se construye un CRM dental (Next.js + Supabase) con bot de WhatsApp con IA en 5 semanas. En el
repo ya hay un bot de prueba con Wechaty. Este plan cubre **solo la Semana 1**: montar el proyecto,
el esquema, la autenticación y el panel básico, además de reubicar el bot existente. Las decisiones
de las semanas 2 a 5 se piden al cerrar cada semana.

### Decisiones ya tomadas por el usuario
| Tema | Decisión |
|---|---|
| Modelo de datos | Con **planes de tratamiento** (plan → items), citas ligadas opcionalmente a un item, pagos ligados opcionalmente a un plan |
| Tenancy | **Un solo consultorio** (sin `clinic_id`) |
| Auth | **Supabase Auth** (email/contraseña) + rol en `staff` + **RLS** |
| Permisos | El dentista ve todo; la **recepción no ve las notas clínicas** |
| WhatsApp | **Twilio en producción, Wechaty solo en desarrollo**, ambos llaman al mismo `handleMessage()` |
| Repo | **Una sola app Next.js** en la raíz; bot en `src/lib/bot/`; Wechaty en `scripts/wechaty-dev` |
| Calendario | **Vista semanal** con filtro por dentista |
| Historial | Ficha del paciente **con pestañas** por sección |

### Revisión del bot existente (resumen)
- `lib/conversation.js` e `lib/intent.js` no dependen del canal y se reutilizan tal cual.
- `lib/scheduling.js` (mock) y `lib/session.js` (en memoria) se quedan así en la Semana 1 y se
  reemplazan por Supabase en las semanas 2 a 4.
- Bug: "cancelar" nunca se alcanza en `handlePendingConfirmation` → se corrige al moverlo.
- `dental-crm-bot.memory-card.json` guarda la sesión de Wechaty → se agrega a `.gitignore`.

## Esquema propuesto (`supabase/migrations/0001_schema.sql`)
- `staff(id uuid pk → auth.users, full_name, role staff_role['dentist','receptionist'], active, created_at)`
- `patients(id, full_name, phone text unique /* E.164, liga con Twilio From */, email, birthdate, allergies, notes_admin, created_at, updated_at)`
- `treatments(id, name, default_price numeric(10,2), default_duration_min, active)` — catálogo
- `treatment_plans(id, patient_id, dentist_id → staff, title, status plan_status['draft','active','completed','cancelled'], created_at)`
  - el total se calcula como la suma de sus items (no se guarda, para evitar inconsistencias)
- `treatment_plan_items(id, plan_id, treatment_id, tooth text null, price numeric(10,2), status item_status['pending','in_progress','done','cancelled'], sort_order)`
- `appointments(id, patient_id, dentist_id, plan_item_id null, starts_at timestamptz, ends_at timestamptz, status appt_status['scheduled','confirmed','completed','cancelled','no_show'], source['panel','whatsapp'], reason text, created_by, created_at)`
  - restricción de exclusión `btree_gist` sobre `(dentist_id, tstzrange(starts_at, ends_at))` en citas no canceladas → la base de datos impide traslapes (la necesitará el bot en la Semana 3)
- `payments(id, patient_id, plan_id null, amount numeric(10,2) > 0, method['cash','card','transfer'], paid_at, received_by, notes)`
- `clinical_notes(id, patient_id, appointment_id null, author_id, body, created_at)` — tabla aparte para que RLS la oculte a recepción
- Vista `patient_balances(patient_id, plan_id, total, paid, balance)`
- Trigger `updated_at`; índices en `appointments(starts_at)`, `appointments(dentist_id, starts_at)` y `patients(phone)`.

### RLS (`0002_rls.sql`)
- Función `public.current_staff_role()` (`security definer`, lee `staff` por `auth.uid()`).
- Todo el personal activo: CRUD en `patients`, `appointments` y `payments`; lectura en `treatments`,
  `treatment_plans`, `treatment_plan_items` y `patient_balances` (la recepción necesita el saldo para cobrar).
- Solo el dentista: escritura en planes, items y catálogo; **cualquier acceso a `clinical_notes`**.
- Sin registro público: las cuentas se crean en el dashboard de Supabase y en `supabase/seed.sql`.

> Punto a confirmar al aprobar: aquí la recepción **puede ver** los planes y sus precios (solo lectura)
> para cobrar. Si no debe verlos, solo tendría acceso a `patient_balances`.

Stack: Next.js (App Router, TypeScript), Tailwind + shadcn/ui, FullCalendar (`timeGridWeek`, MIT),
`@supabase/ssr` y `tsx` para ejecutar el script de Wechaty. Scripts: `dev`, `build`, `bot:dev`, `db:types`.

## Delegación a subagentes
Primero se crean `.claude/agents/backend.md` y `.claude/agents/frontend.md`, cada uno con su alcance
y la regla de detenerse ante cualquiera de las 8 decisiones reservadas al usuario.

1. **Backend** (va primero): scaffold de Next.js en la raíz respetando los archivos actuales,
   migración de esquema, RLS, seed (1 dentista, 1 recepcionista, catálogo, pacientes de ejemplo),
   generación de tipos, clientes de Supabase, middleware, capa `lib/db`, mover el bot a
   `src/lib/bot` + `scripts/wechaty-dev.ts` (con el fix de "cancelar"), actualizar `.gitignore`,
   `.env.example` y el README.
2. **Frontend** (después de tener los tipos): login, layout del panel, lista, alta y ficha con
   pestañas del paciente, y agenda semanal con filtro por dentista y creación y edición de citas
   desde el calendario (se muestra el error de traslape que devuelve la base de datos).
   La UI oculta la pestaña de notas a recepción; la seguridad real la aplica RLS.

El orquestador revisa la salida de cada subagente y, si alguno propone algo que toque una decisión
reservada, se detiene y pregunta.

## Verificación
1. `supabase start` + `supabase db reset` → las migraciones y el seed se aplican sin errores.
2. Pruebas de RLS con SQL (`set role authenticated` + claims de cada usuario): la recepcionista
   recibe 0 filas de `clinical_notes` y no puede insertar en `treatment_plans`; el dentista sí.
3. Insertar dos citas traslapadas para el mismo dentista → error de restricción de exclusión.
4. `npm run build` sin errores de tipos.
5. Manual en `npm run dev`: login con cada rol → dar de alta un paciente → crear una cita en la
   agenda semanal → verla en la pestaña Citas del paciente → registrar un pago y ver el saldo →
   la pestaña Notas solo aparece para el dentista.
6. `npm run bot:dev` → escanear el QR → el bot responde como antes, y "cancelar" ya funciona.
